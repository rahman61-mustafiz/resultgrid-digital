## Remaining findings

1. **E13.Q04 loses required scheduling information.** The draft (QUESTIONNAIRE_V1_DRAFT.md:1508) requires it before approval, including start readiness/date, final date, milestones, timezone and flexibility notes. The app (src/lib/questionnaire/v1.ts:1359) makes it optional and stores a single DATE, with shortened wording. This is a concrete deviation beyond the two disclosed design choices.
2. **Questionnaire validation is incomplete.** Question definitions have no validation schema, and saveAnswerAction trims a string and treats any nonempty value as ANSWERED. Readiness checks presence rather than draft-specific validity. Length, URL, select-membership, structured/repeatable, unit and date relationships are not enforced by this path. Populating all keys does not establish full specification compliance.
3. **Conditional behavior is a disclosed specification deviation.** BUILD_READINESS_QUESTIONNAIRE.md F05 explicitly confirms conditional appearance/requirements. Always-required questions with fallback prose are implemented and documented, but do not satisfy that behavior. Repeatable long text likewise collects notes without the draft's structured validation.
4. **Soft-delete verification can false-pass.** e2e/helpers/qa.ts:236 accepts any sign-in error as proof old credentials no longer work. Network, rate-limit or server errors must fail verification rather than establish SOFT_DELETED; require the expected authentication rejection, preferably also verify deleted account state.
5. **Save failures are not surfaced by the field.** QuestionField.save ignores an error result. Status errors are displayed for the N/A action, but failed answer autosaves have no equivalent error display; a previous Saved indicator can remain visible.
