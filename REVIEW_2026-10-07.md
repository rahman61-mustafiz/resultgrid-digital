# Option B review — 7 October 2026

## Decision

The reported suites pass where rerun so far, but Option B should not receive unconditional acceptance. Close the stored-answer validation gap before treating the approval boundary as complete. Priority #7 planning can proceed; implementation should retain these readiness and approval fixes as acceptance gates.

## Findings

### High: stored malformed answers can pass the app's approval readiness gate

`src/lib/questionnaire/engine.ts:357` checks structured field requirements and semantic rules without calling `normalizeAnswerValue`. For SINGLE_SELECT and DATE answers it checks only that the value is a string, then returns no issues. Structured dates and select options likewise are not revalidated for shape/membership here.

A temporary Playwright unit audit used all valid fixture answers except:

- E01.Q04 = `INVALID-STAGE`.
- E13.Q04 = `{ startDate: "2026-02-30", finalDate: "2026-02-31", milestones: "No interim milestones" }`.

Actual result: `{ "isComplete": true, "problems": [] }`.

The approval path calls this same engine on the export snapshot (`src/lib/export/build-export-content.ts:79`) and proceeds when `built.readiness.isComplete` is true. The database's Owner RPC accepts malformed values, as already disclosed. The README claim that such values cannot be approved through the app is therefore incorrect. Fingerprints protect against concurrent changes; they do not validate the values.

This reproduction exercised the actual engine locally and traced its use by the approval action; it did not insert malformed values into live data or perform a browser approval of them. The temporary audit test was removed afterward.

Fix: apply shape/type/option/date validation to every applicable stored answer before semantic readiness checks, treating invalid shapes as readiness problems. Add regression coverage for malformed scalar and structured values at the approval boundary. SQL duplication is not needed for this fix.

### Medium: mark-ready still has a read/check/write race

`src/app/(app)/projects/[id]/readiness/actions.ts:25` reads project type and answers in separate queries, checks readiness, then calls `submit_project_for_review` with only the project ID. The RPC locks the project but neither validates the checked snapshot nor receives a fingerprint. An invalid answer saved after the check but before submission can therefore be marked READY_FOR_REVIEW. The save RPC leaves an already-INCOMPLETE project INCOMPLETE, so it does not prevent that interleaving.

Approval has the stronger snapshot/fingerprint protection; this finding concerns mark-ready status and its ledger event. It is established by code inspection, not a live concurrent reproduction. Fix by checking readiness from a coherent snapshot and verifying that snapshot under the transition lock, with a concurrent-save regression.
